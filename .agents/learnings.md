# Implementation Learnings

Reference document for AI agents. These are hard-won insights from past RFC implementations and issue resolutions. Read the relevant section before starting work on any RFC implementation or any change that touches the parser, typechecker, or lowering stages.

## General pipeline pitfalls

- **Async result passthrough should stay direct**: when an async helper already returns `Result`, prefer `await helper(...) ?` over matches that rewrap `Ok(_) => Ok(None)` / `Err(err) => Err(err)`; Incan lowers `await expr?` correctly, and the explicit rewrap just adds showcase-hostile noise. (IncQL cleanup, April 2026)
- **Boolean equality checks are noise**: avoid `expr == false` / `expr == true` in Incan code; prefer `not expr` or `expr` directly so conditions read as logic instead of desugared comparison. This matters especially in planning/lowering code where visual noise compounds quickly. (IncQL cleanup, April 2026)
- **Bridge modules need contract docs**: adapter/bridge files that translate between internal and public ASTs must document directionality, error behavior, and unsupported shapes up front; sparse rustdocs in these boundaries cause incorrect call-site assumptions and fragile follow-on changes (RFC 027 Phase 6).
- **Ceremony helpers need a job**: tiny wrappers like `empty_*()` or `_clone_*()` are anti-patterns when they only spell `[]` or a one-line copy the language already expresses clearly; keep helpers only when they carry real semantics such as generic type witnesses, cross-stage invariants, or non-obvious boundary contracts. (IncQL showcase cleanup, April 2026)
- **Dependency policy changes need approval**: when `cargo-deny` surfaces new licenses or advisories, do not add global license allows or advisory ignores as a convenience step; first identify the exact dependency path and get explicit approval for any policy exception versus dependency upgrade. (Wasmtime/deny cleanup, April 2026)
- **Dual module paths can collide**: when Incan emits Rust modules, having both a file module and directory module for the same name (`foo.incn` and `foo/mod.incn`) can map to conflicting Rust paths (`foo.rs` and `foo/mod.rs`) and fail with module ambiguity (`E0761`); pick one module shape and keep it consistent across the package.
- **Duckborrowing is codegen policy**: when work touches lowering/emission, call arguments, collection literals, returns, match scrutinees, Rust interop, or generated `.clone()`s, route ownership through `src/backend/ir/ownership.rs` / `ValueUseSite` and update trait-bound inference/tests instead of adding local `.clone()`, `.as_ref()`, `str(...)`, or `.into()` workarounds. (Issue #121, April 2026)
- **Forward receivers by borrow shape**: when lowering wrappers or adapters around methods, model `self` as the callable's actual receiver borrow (`&Owner` or `&mut Owner`) and pass that through directly; inserting `.clone()` hides a compiler lowering shortcut as user-visible ownership behavior and breaks mutable receiver support. (RFC 036 / issue #170)
- **Incan gaps belong in the backlog**: when a minimal probe proves that Incan cannot yet express a required operation, file the missing capability as a bug, chore, or RFC before introducing a foreign fallback. Keep any temporary Rust or C bridge narrow, link it to that backlog item, define its removal condition, and do not move surrounding product semantics or orchestration out of Incan.
- **PR conflict resolution must use `origin/main` as the merge base**: when a user asks to merge main or resolve PR conflicts, inspect and merge against `origin/main`, not the local `main` branch copy. Local `main` can lag the remote and give a false “merged main” result while GitHub still reports conflicts. (RFC 015 branch, April 2026)
- **Match ladders are a smell**: in authored `.incn` code, avoid nested `match` ladders that only peel `Option`/enum variants before continuing; prefer `if let`, early returns, or a focused `match` with shallow arms. Do not "fix" the ladder by creating a forest of one-use helpers; keep helpers only when they name a real concept. (IncQL #25 source-quality cleanup, May 2026)
- **Name repeated kind checks**: when the language lacks grouped pattern arms, do not duplicate long `kind == A or kind == B ...` chains across functions; hide the grouping behind one predicate/helper so later enum-surface changes do not drift between call sites. (Prism output-column cleanup, April 2026)
- **Never expose local paths**: Shareable artifacts must use repo-relative paths or plain command names; absolute workstation paths like `/Users/...` leak personal details and should be blocked in hooks and avoided in docs, issues, PR text, and examples. For GitHub issues/PRs, run the check before the first create/update call because edit history can preserve the original text.
- **New AST variants need full pipeline wiring**: adding a `Statement`/`Expr` variant is never parser-only; you must update formatter, feature scanners, typechecker, lowering, and any AST bridge layers in the same change or compilation/tests will break in scattered places (RFC 027 Phase 6).
- **Method defaults need emission tests**: method default arguments can pass typechecking but still emit invalid Rust if the method-call emitter does not synthesize omitted defaults; when adding or using method defaults, include a run/codegen test that calls the method with omitted arguments. (Issue #286)
- **Stdlib function defaults cross stages**: imported stdlib free-function defaults must be preserved from AST loading through typechecking, lowering, and emission; a typechecker-only default fix can still produce generated Rust calls with missing arguments. Add end-to-end run coverage when public stdlib APIs rely on omitted defaults. (RFC 064 / issue #342)
- **String literal wrappers are showcase noise**: avoid `str("literal")` when a plain string literal communicates the same value; use explicit ownership conversion like `"literal".to_string()` only at Rust/container boundaries that currently require owned `str` values. (IncQL Substrait cleanup, April 2026)
- **Typechecker passing does not mean lowering works.** A feature that typechecks correctly can still generate invalid Rust if the lowering stage doesn't handle the transformation. Always verify both stages independently. (Learned from RFC 021: field aliases typechecked but lowering didn't translate them, producing broken Rust.)
- **Stdlib dogfooding must fix compiler gaps**: when idiomatic `.incn` stdlib source exposes a typechecker/codegen mismatch, fix the compiler boundary and add an end-to-end run test instead of reshaping stdlib code to avoid the feature. String and bytes iteration in RFC 064 exposed this in `for`/`enumerate` lowering.
- **Reject out-of-scope features at the typechecker**, not silently. When an RFC says "X is not supported", add an explicit diagnostic in the typechecker. Don't leave partial support that passes typechecking but fails in lowering or emission.
- **Parser should own type-sugar desugaring**: If a surface spelling must never reach lowering/emission (e.g. function-type sugar vs. a dedicated AST node), desugar in the parser to the canonical `Type::*` shape instead of duplicating normalization in `resolve_type`/symbols—two sites drift, and the resolver-only path can lag so the sugar leaks into generated Rust.
- **`Program` struct stability**: adding fields to `Program` breaks all literal construction sites. Use `#[derive(Default)]` + `..Default::default()` in tests — never explicit field lists in test helpers.
- **Resolved semantics beat lowering guesses**: when typechecking resolves overloads, trait dispatch, callable kind, or type-directed behavior, carry that decision through `TypeCheckInfo`/IR instead of hardcoding method names or argument shapes in lowering/emission; feature-specific lowerings can pass one RFC while creating unmaintainable compiler policy. (RFC 056 / issue #291)
- **Single-source plans prevent split brain**: callable identity, defaults, ownership/coercion, union wrapper identity, Rust metadata, and vocab helper-call behavior must flow through canonical planning data instead of local typechecker/lowering/emitter guesses; same-module success is not enough if imported, reexported, packaged, or test-batched code can observe different behavior. (v0.3 RC cycle, June 2026)
- **Use `IrType::incan_name()` for user-facing type strings**, not `IrType::to_string()` (which returns Rust types like `String` instead of `str`).

## Rust: `unwrap` / `expect` ban vs. `unwrap_or`

- **`unwrap_or` is not banned like `unwrap`**: AGENTS forbids `.unwrap()` and `.expect()` because they panic on absent/error values; it does **not** forbid `.unwrap_or(...)`, `.unwrap_or_else`, or similar fallbacks. Converting `try_into().unwrap_or(saturate)` into a `match` to “avoid unwrap” is misguided and can fail `clippy::manual_unwrap_or` with `-D warnings`.

## Testing strategy

- **Always test both typechecker and codegen.** Typechecker unit tests validate semantics; codegen snapshot tests verify end-to-end output. Neither alone is sufficient.
- **Boundary parity is coverage**: a language or stdlib feature is not release-ready just because it passes local/direct tests; add coverage for import, reexport/facade, package consumer, test-batch, and dependency/vocab-generated call paths when the feature can cross those boundaries. (v0.3 RC cycle, June 2026)
- **Downstream acceptance should run early**: when IncQL or another downstream project exercises the surface being changed, run its focused acceptance before RC hardening rather than after local compiler tests pass; downstream failures often expose package, metadata, and generated-Rust paths that synthetic fixtures miss. (v0.3 RC cycle, June 2026)
- **Performance regressions need evidence gates**: long silent compiler phases, repeated metadata prewarm work, or unexpectedly slow pre-commit/CI steps should be measured and given progress output or budgets; "eventually completes" is not enough for release tooling. (Issues #707/#723/#736, v0.3)
- **Review closeout requires repo gates**: do not declare a review or implementation loop complete on targeted parser/typechecker/codegen checks alone; run `make pre-commit` (or the repo’s full gate) before closeout, because formatter/clippy/all-targets failures can still surface missing imports, feature-gated compile errors, or drift outside the exercised feature slice. (RFC 049 / issue #333)
- **Conformance fixtures belong in tests**: production conformance modules should define scenario contracts and validators only; synthetic fixture plans and hardcoded sample literals belong in test-local builders so contract APIs stay clean and reusable.
- **Extern fixture coverage must stay real**: when removing or renaming a Rust host-boundary symbol, update generic extern-delegation fixtures/snapshots (for example `rust_extern_delegation`) alongside feature-specific snapshots; otherwise test coverage keeps validating dead runtime paths instead of the current boundary shape. (Issues #301/#302)
- **Snapshot tests must exercise features in expressions**, not just declarations. A model that declares an alias but never uses it in an expression won't catch lowering bugs.
- **Test both `From` and `RustFrom` import forms** when changing import handling — they share `parse_import_items(rust_item_names)`; only `RustFrom` passes `true` so Rust symbols may be Incan keywords (e.g. `import type as proto_type`). Incan `from m import ...` keeps `rust_item_names=false`.
- **Vocab packages need full toolchain tests**: scoped vocab fixes must be verified through parse/check, `fmt`, `fmt --check`, `incan test`, package consumers, and nested consumers; formatter and test-runner activation can drift from ordinary `--check` even when the desugarer itself is correct. (Issues #724/#727/#729/#730/#735/#756, v0.3)

## Oven Alpha composition and release trust (v0.5 rc cycle, August 2026)

- **A green compiler suite does not prove a working release**: 2,600+ passing unit/integration tests coexisted for weeks with a flagship consumer (IncQL) that could not build or run at all. Every defect lived at a composition boundary between independently built artifacts — invisible to any test that compiles everything in one process. A real external consumer project (the IncQL quickstart) exercised as a release gate would have caught the regression at dev.41 instead of rc4.
- **The release pipeline must run in CI before it is trusted**: `toolchain_release.yml` only triggers on version tags, so the v0.5 packaging path (`package_archive.sh` → `bake-loafs`) went months broken with nobody able to notice. Any workflow that only fires on release day is untested by definition; give it a dispatch-based dry run in ordinary CI.
- **Same package + same version ≠ same compiled artifact**: two independent Cargo resolutions of identical source produce byte-distinct, ABI-incompatible rlibs (feature unification and compilation context feed the SVH). Composing independently resolved closures without unifying resolution silently links two instances of one crate — harmless for pure code (`memchr`), catastrophic for crates with process-wide state (`tokio`: `block_on` enters a runtime through one instance's thread-locals while dependents compiled against the other instance see "no reactor running"). Any future Oven resolver must either unify resolution across all fragments or detect same-version digest divergence and refuse/route.
- **Verify links at the binary, not the build log**: the duplicate-crate diagnosis came from `nm <binary> | grep -oE "Cs[a-zA-Z0-9]+_5tokio" | sort -u` — two distinct v0 mangling crate hashes for one crate name is the smoking gun. A successful build plus a runtime panic means inspect what was actually linked.
- **Detector-as-router beats detector-as-wall**: an eager pairwise closure comparison over-fires (suite `memchr` divergence that Cargo handles fine), an extern-only check under-fires (`tokio` enters transitively, never as a named extern). The working shape: compare provider vs consumer registry catalogs for same-version digest divergence, and on conflict *route* executables through one unified `cargo build` of the generated project (the correct-by-construction v0.4 path, kept in-tree) instead of erroring — fail closed only where no fallback exists (library outputs).
- **Guard every selection path, not the one you debugged**: the conflict check first landed only on the stored/extension bake path; consume-only runs selected the imported packaged-provider composition (`uses_packaged_provider_closure`) and silently rebuilt the broken binary. When adding a safety check to `bake_oven_project`-shaped dispatchers, enumerate all `OvenDirectRustcPlanSelection` variants and prove each one passes through it — and retest from a *clean* consumer state, because residual store state can make a broken path look fixed.
- **Keep the retired-but-correct path compiled**: the v0.4 Cargo build survived as `#[cfg(test)]` fixture code and could be resurrected in hours as the production fallback; if it had been deleted, the router option would not have existed on release timeline. When replacing a correct system with a faster one, keep the correct one dormant and reachable until the replacement has consumer-grade evidence.
- **Bisect non-atomic history by version checkpoints, not commits**: inside large squashed-PR stretches, intermediate commits are unbuildable or unpackageable; bisecting over `Cargo.toml` version-bump commits (dev.N labels) gives testable checkpoints. And when a checkpoint needs local patches just to build, stop bisecting — the defect is architectural, and reading the composition code beats another rebuild cycle.
- **A clean room without Rust is the easy half of the test**: rc4 through rc6 all passed container installs and still broke real users, because the containers had *no* Rust. Loafs are sealed against an exact `rustc --version` string (`verify_rustc_identity` demands equality), so the machine that fails is the one that already has Rust at some other version — precisely the machine a developer is using. Any install-path clean room must cover both states: no Rust at all, and Rust deliberately pinned to a version the release was not built with.
- **A floating channel cannot pin a sealed artifact**: the release manifest advertised `rust_toolchain.channel: "stable"` while `dtolnay/rust-toolchain@stable` independently resolved "stable" on each packaging runner, and nothing recorded what was actually used. Shipping artifacts that are valid only under one exact compiler means the manifest has to name that compiler concretely (`1.98.0`), recorded per host at packaging time and required to agree across hosts before publishing — otherwise a Rust release landing between packaging and installation silently invalidates the release.
- **Isolate by reading the layout, not by asking the tool**: resolving Incan's own toolchain through `rustup which` with only `RUSTUP_HOME` set is not isolation — `RUSTUP_TOOLCHAIN` and a directory `rust-toolchain.toml` both outrank a home's default, so the user's environment can still select a toolchain that does not exist in Incan's home. Reading `<incan-home>/rust/toolchains/<channel>-*/bin/<tool>` directly is exact, immune to ambient override, and cheaper than a subprocess. Discovery must also canonicalize `current_exe()`: the installer links commands as symlinks and `current_exe` is documented to be allowed to return the symlink, which would hide a non-default `--incan-home` from the ancestor walk.
- **Package managers that skip the installer skip the fix**: npm and pipx delegate to `install-incan.sh` and therefore inherit toolchain provisioning for free; Homebrew installs prebuilt commands directly and does not. When an installer gains a correctness responsibility, audit every distribution channel for whether it actually runs that installer, and give the ones that do not an explicit, version-exact instruction in their own surface (the formula's `caveats`).
- **Library bakes needed the unified-Cargo fallback executables already had**: a root library with heavy registry dependencies (IncQL + DataFusion) cannot always be composed from independently compiled parts, and direct-rustc then fails with crate-loading errors about crates the user never named. The fix is the same one executables use -- rebuild through one Cargo resolution, which is internally consistent by construction (`cargo_fallback_bake_oven_library`). Trigger only on crate-loading codes (`E0460`/`E0461`/`E0463`/`E0464`); generated Rust never produces those from a type error, so a genuine compile failure cannot be silently retried.
- **rustc's newer JSON records defeat the structured decoder**: diagnostics tagged `"$message_type":"diagnostic"` are not recognized, so `OvenRustcDiagnosticReport.diagnostics` comes back empty and the entire transcript lands in `unstructured_output`. Any logic that inspects diagnostic codes must scan both, or it silently sees nothing -- this is why a crate-loading failure surfaced as raw rustc noise instead of being handled.
- **A gate that finds nothing must fail, not pass**: the IncQL gate reported `compiled tokio instances: 0` and passed, while the binary carried 9,146 tokio symbols. The unified-Cargo binary uses *legacy* mangling, so the v0 pattern `Cs<hash>_5tokio` matched zero and read as clean. Counting evidence that can legitimately be absent is the same defect as timing a build that never ran: assert that the measurement itself succeeded, and when counting duplicate crate instances by rlib, scope it to the binary's own profile so a debug/release pair is not misread as duplication.
- **The caller-owned store dedups against the Loaf, and that invariant is violated**: the store retains only registry crates the toolchain Loaf does not ship (`log`, `ppv_lite86`, `serde`, `regex` are all in the Loaf and absent from the store), expecting consumers to link the Loaf's copies. That is sound only if the store's crates were compiled *against* those exact copies -- they are not, because Cargo resolves and builds its own and they are then dropped. DataFusion in the store records a `ppv_lite86` that exists nowhere, rustc finds the Loaf's different compilation, and rejects the chain (`E0460`, surfacing as `E0463` for the named crates). It is the duplicate-tokio family on the Loaf-vs-store axis, which `caller_owned_provider_registry_conflict` never examines because it only compares a provider against a consumer -- so a root library with heavy registry dependencies does not even fail closed, it dies in raw rustc errors.
- **Stale provider artifacts masked a broken release for two release candidates**: IncQL appeared to work because `target/lib/oven/package-loafs.json` had been baked by rc4 and was still on disk; rc5 and rc6 refuse it ("rebake the provider with this Incan release") and the rebake fails. Verifying a consumer without deleting provider *and* consumer build state proves nothing about the release under test. Delete both, or the evidence is about last month's compiler.
- **A reference consumer must be clean, and the gate should enforce it**: the IncQL gate failed against both a debug compiler and a freshly packaged release toolchain, and neither result was interpretable — the checkout carried uncommitted edits (a modified tracked `incan.lock` and an edited `.incn` source). A dirty subject makes a failure unattributable to the compiler under test, and makes an A/B against an older release useless too (rc6 failed *earlier*, at typecheck, because it could not compile the edited source). Cleaning it is not an option when the edits are the maintainer's work in progress, so `scripts/gate_incql.sh` now refuses to run on a dirty checkout unless `--allow-dirty` is passed.
- **Chase the real invocation, not a reduced one**: reducing the IncQL failure to a minimal `rustc --extern` command produced three consecutive wrong conclusions (missing rlib, malformed crate name, broken store artifacts), because the reduction dropped the `-L dependency` paths that make the failure what it is. The control that exposed the mistake was running a *known-good* crate through the same reduced probe: the Loaf's own `serde` failed it identically. Replicating the full original search path immediately produced the true error, `E0460 found possibly newer version of crate ppv_lite86` — a duplicate-crate-closure conflict, not a missing artifact. When reducing a failing command, verify the reduction still passes on a known-good input before trusting what it says about a bad one.
- **Prove the artifact under test was rebuilt, not just that something ran**: four separate wrong conclusions in one session traced to the same root -- trusting a proxy for "this is the code I changed". A passing exit code (IncQL, carried by rc4-baked artifacts), a file timestamp (benchmarks that looked rebuilt but reused pre-fix binaries), a symbol pattern that matched nothing (the tokio counter reading 0 on a legacy-mangled binary), and a cached SDK store (four examples failing against a store 30 minutes older than the Loaf). In every case the measurement was fine and the subject was wrong. Before believing a result, establish that the artifact was produced by the current code: delete the build state, or capture the compiler invocation, or assert a value that could only come from the new build. A benchmark that reuses a stale binary reports a confident number about the wrong program.
- **A benchmark must prove the work happened**: timing `incan build` after a source edit looked like a clean 0.4-vs-0.5 comparison and was meaningless, because 0.4.0 reports a successful build in ~40ms without rebuilding — `incan run` still prints the previous value, while a clean rebuild picks the change up. Any harness that times incremental work has to verify the change reached the artifact (edit something observable, run it, assert the new value) and record a refusal rather than a fast number when it did not. A fast measurement of a no-op is worse than no measurement, because it reads as a win.
- **Deep expressions need a compiler-sized stack, not a diagnostic**: a long `"a" + "b" + ...` chain nests the AST once per operand, and past roughly 1,000 terms the recursive walk exhausted the default main-thread stack and aborted `incan` with `fatal runtime error: stack overflow`. A stack overflow is not a catchable Rust panic, so no diagnostic is reachable from inside it; the fix is to run compilation on a thread with a large stack (`src/compiler_stack.rs`, honoring `RUST_MIN_STACK`), which is what `rustc` does for the same reason. The language server needs the same treatment via `tokio::runtime::Builder::thread_stack_size`, since it typechecks on worker threads and would otherwise die on an open file.

- **A source checkout is not the toolchain that ships**: the compiler resolves stdlib `.incn` sources through a compiled-in `CARGO_MANIFEST_DIR` fallback, and the integration suite sets `INCAN_STDLIB` to the checkout, while a release archive ships **zero** `.incn` files. Any defect living in that gap is structurally invisible to `make test`, to `make examples`, and to every locally built binary. It hid `@derive(Clone)` producing no callable `clone()` in installed toolchains for seven release candidates -- 47 errors in the flagship consumer while the same sources built clean from a checkout, and three successive fixes plus a regression test all "passed" because they were validated in the wrong configuration. Verify anything touching stdlib metadata, trait/derive resolution, or SDK providers against a real archive: `package_archive.sh` takes about four minutes locally, and the tell that you have the right configuration is `find <extracted> -name '*.incn' | wc -l` returning 0.
- **Prove a check can go red before trusting it green**: three separate gates in one release could not fail. The clean room *printed* the machine's default Rust instead of asserting it, so it passed whether or not Incan reconfigured a user's toolchain -- the one property that scenario exists to prove. The IncQL gate built in an empty `INCAN_HOME`, which cannot validate a released archive at all, because a release's Loafs bind to the exact Rust its installer provisions and every shipped Loaf is rejected as incompatible. The version gate covered hand-written npm/pip literals but not `Cargo.lock`, and a stale lock killed a tag on all three runners. Each looked thorough while measuring nothing. When you add or accept a check, run it against a known-bad input once; a check never observed failing is a claim, not evidence.
- **Selecting a toolchain's Cargo does not select its compiler**: Cargo takes `rustc` from `RUSTC` or from `PATH`, and on any machine with Rustup installed `PATH` reaches the shim, which resolves to the *user's default* toolchain. Incan's unified-Cargo fallback therefore built one dependency graph with Incan's Cargo and someone else's compiler, which Cargo reports late and indirectly as `found crate X compiled by an incompatible version of rustc` -- naming a dependency, saying nothing about two toolchains being in play. Anything that selects a provisioned Cargo must pin the matching `RUSTC` alongside it (`cargo_command` in `backend/project/runner.rs`); the Loaf baker and compatibility publisher already did, which is why only one path was wrong. Affects every user whose default Rust differs from the pinned release -- the normal case.
- **Pinning a Rust version inherits that version's packaging bugs**: Rust 1.98.0 for `aarch64-apple-darwin` links `rust-lld` against `libLLVM.dylib` through an `@rpath` resolving to `lib/rustlib/<target>/lib/` but ships the dylib only in the toolchain's own `lib/`, so nothing links for any target needing `rust-lld` -- on Incan the `wasm32-wasip1` vocab companion. Neighbouring releases are unaffected (earlier ones link LLVM statically, nightly ships the dylib in both places), and CI could not see it because the runners are Linux and x86 macOS. When the installer provisions an exact toolchain, it owns that toolchain's defects too: repair them at provisioning time, guarded so the repair no-ops once upstream fixes it.
- **Gate generated files the release builds with, not just hand-written ones**: bumping the workspace version without letting Cargo refresh `Cargo.lock` leaves the two disagreeing, and every release job builds with `--locked`, so the mismatch fails on the runner after the tag is pushed rather than locally before it. A version gate that checks only the literals a human types will keep missing this. `v0.5.0-rc9` died exactly this way and published nothing.

## Oven ownership-decision issues (#870/#1034 sub-issues)

- **Check for a de facto API before designing a new one**: a "decide where this logic belongs" issue can default to assuming a brand-new module is needed. Before that, grep for `crate::<candidate_source_file_stem>::` across the repo to find `pub(crate)` functions in the source file already called from outside it, and read the target module's own doc comment for a stated charter. In #1094, 13 of `build.rs`'s 25 `pub(crate)` functions were already consumed from `lock.rs`/`oven.rs`/`execution.rs`, and `src/oven.rs`'s module doc already frames itself as "a narrow, removable boundary" — together these turned "design a new API" into "relocate an API that already exists in practice and respect an existing charter," a materially lower-risk decision than starting from a blank module.
- **Flag tangential findings, don't scope-creep or unilaterally file for them**: a decision issue's own inventory often turns up code that doesn't cleanly belong to the extraction being decided (in #1094, a `CompiledProviderMetadata`/provider-metadata-projection block and a `LibraryReexportResolver` sitting in `build.rs` that are actually provider/library-manifest semantic logic, with no existing #1034 sub-issue covering their placement). Record the finding explicitly as out of scope in the decision document rather than either widening the current issue to cover it or filing a new issue on your own initiative — let the maintainer decide whether it warrants one.

## Agent orchestration

- **Loop identity gates resumes**: Ralph-loop state must record the active repo, issue/RFC/milestone allowlist, and verification-only downstream repos; on resume, filter stale slices before scheduling work or consumer-repo validation can turn into unrelated implementation. (Incan 0.5 Ralph-loop scope drift, July 2026)
- **Diff-based gate scripts need `--base` once changes are committed**: `scripts/check_changed_rustdocs.py`'s no-argument default only diffs uncommitted staged+unstaged changes; running it after `git commit` (with nothing left uncommitted) silently checks zero lines and prints a false "gate passed". Any diff-based check (this script, and by extension anything with the same `git diff`-against-working-tree shape) must be re-run with `--base <merge-base-or-ref>` once the change it is verifying is committed — a "passed" result from before the commit does not carry over. Caught in PR review after 31 undocumented functions slipped past a stale "rustdoc gate passed" claim on #1103. (Incan 0.6 Body IR v0, August 2026)

## Parser and lexer patterns

- **Parser warning infrastructure**: `Parser.warnings` stores non-fatal warnings as `Vec<CompileError>`. On success they move into `Program.warnings`; on error they fold into the error vec with `ErrorKind::Warning`. This is the canonical way to add syntax nudges without blocking compilation.
- **Lexer bracket depth handles multi-line for free**: `bracket_depth` suppresses `Newline`/`Indent`/`Dedent` inside `(...)`. Check lexer bracket tracking before adding complex multi-line parser state.
- **Soft keywords stay as identifiers in the lexer**: emit `Ident("async")` etc.; the parser promotes them to keywords only when the activating namespace is imported. Activation is tracked per-file via `active_soft_keywords`.

## Stdlib and registry patterns

- **`STDLIB_NAMESPACES` is the single source of truth** for which `std.*` modules exist, how stub paths resolve, and which imports activate soft keywords. Extend the registry rather than adding hardcoded special cases.
- **Incan stdlib source is Incan**: for `.incn` stdlib modules, use idiomatic Incan surfaces such as value enums, defaults, `if let`, and source docstrings; do not paper over compiler gaps with Rust-shaped `.clone()`, `.to_string()`, or verbose match scaffolding. This does not ban normal ownership/conversion code in Rust compiler/runtime files. (Issue #286)
- **Incan capability requires evidence**: do not assume the language cannot express a design just because it is new or because older work lacked a feature; search current `.incn` stdlib/examples/tests or run a small probe before narrowing scope or adding Rust/backend fallback. Record the exact missing primitive when a fallback is truly needed. (RFC 060 / issue #338)
- **Incan stdlib prose is authored surface**: public `.incn` stdlib APIs should use the `std.fs` docstring shape: summary, semantic notes, and `Args` / `Returns` / `Example` sections where useful. Strategic comments should explain non-obvious protocol transforms or compiler boundary workarounds, while sentinel initialization and generated-looking match scaffolding should be treated as anti-patterns. (RFC 060 / issue #338)
- **Incan source layout must teach**: `.incn` implementation files should honor the Zen of Incan for Python-oriented readers: descriptive docstrings, enough inline comments for deep implementation code, helpers grouped near their public/external callers, and aliases/partials/properties used instead of hand-written wrappers when they better state the API relation. (v0.3 source-quality review, May 2026)
- **Incan boilerplate removal should expose compiler work**: when removing redundant `.incn` stdlib methods that duplicate trait defaults, fix default-method lowering and generated import retention instead of re-adding boilerplate to satisfy Rust emission. Keep the Incan source Python-clean and add compiler regressions for the boundary that failed. (RFC 060 / issue #338)
- **Result combinators should stay available to stdlib code**: when `.incn` stdlib cleanup wants `Result.map`, `map_err`, `and_then`, or `or_else`, do not fall back to explicit branch scaffolding without first testing the combinator path. Captured closures are valid callbacks; if they misemit, fix result-combinator emission and add an end-to-end run test. (Issue #571 / RFC 060)
- **Exact numerics need end-to-end preservation**: when a stdlib implementation relies on exact-width arithmetic such as `u128`, fix the typechecker, lowering result type, and emission plan together; otherwise expressions can typecheck but lower to default `int` helpers such as `py_mod_i64` and fail in generated Rust. (Issue #547 / RFC 060)
- **Dogfood protocol surfaces first**: before making a stdlib protocol feature compiler-owned, inspect existing stdlib/IncQL dogfooding and try `.incn` default methods/carrier types as the semantic source of truth; compiler known-method paths should be bridges or optimizations, not the first assumed implementation. (RFC 088 / issue #127)
- **Dogfooding is not a facade**: when Ralph-looping language or stdlib work that is meant to be implemented in Incan, do not satisfy the surface by creating a thin `.incn` wrapper over a custom Rust backend. Direct `from rust::` imports of existing crates/primitives are allowed when the `.incn` module still owns the behavior, but bespoke `incan_stdlib::feature` Rust modules that hide the feature logic defeat the point. (RFC 060 / issue #338)
- **Dogfooding includes combinators**: in `.incn` stdlib source, use current language ergonomics such as RFC 070 `Result` combinators (`map`, `map_err`, `and_then`, `or_else`) instead of verbose `Ok`/`Err` matches that only transform or chain one branch; if this exposes callable/codegen gaps, fix the compiler and add an end-to-end regression. (RFC 064 / issue #342)
- **Dogfood stdlib modules first**: when adding a user-facing stdlib module, start with a source-defined `.incn` implementation and fall back to Rust only after proving the language cannot express or compile the needed behavior; Rust adapters can hide compiler gaps that stdlib dogfooding should expose. (RFC 047 / issue #204)
- **Stdlib stubs (`stdlib/*.incn`) are IDE-only** — the prelude isn't wired into compilation. For core surface types like `FieldInfo`, also register them in `incan_core::lang::surface::types` and map to the runtime Rust type in IR emission.
- **Metadata-driven decorators keep their extern shell**: `std.testing` markers (`skip`, `xfail`, `slow`, `fixture`, `parametrize`) cannot be converted to plain Incan wrappers just because runtime calls are rejected; `src/frontend/testing_markers.rs` extracts semantics from `@rust.extern(metadata={...})` in `stdlib/testing.incn`, so removing that shell breaks discovery even if normal execution still passes. (Issue #302)
- **Runtime facades must match generated imports**: if codegen emits `incan_stdlib::r#async`, the runtime crate must export that module tree.
- **Prefer `.incn` declarations over synthesized `FunctionInfo`**: if a public stdlib function exists, use a local `.incn` wrapper so the AST loader extracts its signature from source. Handwritten `FunctionInfo` drifts.

## Wiring: CLI and LSP

- **CLI wiring for warnings**: surface `ast.warnings` via `eprint!` in `common.rs`'s `collect_modules()` — this automatically covers all CLI commands.
- **LSP wiring for warnings**: after `parser::parse()` succeeds, loop `ast.warnings` and push each through `compile_error_to_diagnostic()` before typechecking.
- **LSP is feature-gated**: `cargo build --features lsp` (or `make build`, which enables it) produces `incan-lsp`. For local dev, `make build` symlinks `~/.cargo/bin/incan-lsp` to `target/debug/incan-lsp` unless CI / `INCAN_SKIP_CARGO_BIN_LINK=1`; use `make install-lsp` or `cargo install --path . --features lsp --bin incan-lsp --force` when you need a crates.io-style install instead.

## Docs and RFC tooling

- **Comment prose belongs to rustfmt**: in this repo, do not manually hard-wrap prose comments or rustdoc to 80/100/120 columns; write them naturally and run `make fmt`, because the repo rustfmt config handles long comment wrapping but will not reliably undo awkward short-wrapping after the fact. (RFC 016 / issue #327)
- **Explanation comments are part of the surface**: in Incan-family codebases, especially planning/lowering/interop code written in Python-shaped syntax, short explanatory comments are not optional garnish; they reduce the “hidden magic” effect for readers who are seeing compiler- or systems-level work in an unfamiliar surface language. Remove stale comments, not merely comments that an expert finds obvious. (IncQL readability policy, April 2026)
- **Implementation docs must be user-facing**: RFCs and release notes do not satisfy user documentation for a new language/compiler feature; when behavior is user-visible, update the authored explanation/how-to/tutorial/reference docs where users actually learn the surface, not just the RFC or changelog. (RFC 049 / issue #333)
- **Markdown prose should not be short-wrapped**: when generating authored Markdown documents, do not manually wrap prose to artificial line lengths; use natural paragraph lines unless the structure itself requires line breaks, because short-wrapped prose reads fragmented and creates noisy diffs for whitepapers, RFCs, and research docs. (Pallay research docs, April 2026)
- **RFC phase before code**: when using `ralph-loop` for an RFC implementation, move the RFC to `In Progress` and confirm the implementation plan/checklist before writing code; do not treat lifecycle edits and phase confirmation as a post-implementation cleanup step. (RFC 016 / issue #327)
- **RFC PR means implementation PR**: in RFC headers, `RFC PR` is the PR where the RFC was implemented or shipped, not the proposal issue or the PR that first added the Draft RFC document. Leave it unset for Draft or otherwise unimplemented RFCs even when a proposal issue exists.
- **North-star first for RFCs**: when a maintainer asks for an RFC, start from the desired end-state contract and only discuss incremental slices after that north-star is explicit; do not reflexively shrink RFC scope into the smallest implementable change unless the user asks for rollout planning.
- **Pre-RFC research lives in root `__research__`**: capture exploratory north-star notes, spikes, and design parking lots under the repository root `__research__/` directory, not `.agents/`; `.agents/` is for reusable agent workflows/learnings rather than project research artifacts. (Android/Incan rustc bridge ideation, May 2026)
- **RFCs are decision records, not diaries**: keep RFCs as moment-in-time intent/status documents, and move implementation details, drift notes, and current behavior into regular docs or release notes with issue links instead of rewriting RFC narrative in flight.
- **Generated references are gates**: when adding or changing a stdlib namespace or language registry entry, run `cargo run -p incan_core --bin generate_lang_reference` and verify no diff before publishing; `make pre-commit` alone may miss generated `language/reference/language.md` drift that CI enforces. (RFC 065 / issue #343)
- **Implementation work must check dev version first**: before landing an implementation on the active dev line, verify the repo's actual source-of-truth version instead of assuming an older release train from stale docs or a worker worktree; at minimum, implementation work should bump `-dev.N` by one and update any versioned docs/release-note targets that track `main`. (Issue #333, April 2026)
- **Stdlib closeouts need reference-nav parity**: when a stdlib issue changes a module's implementation shape or canonical docs path, update the stdlib reference index, MkDocs nav, and any legacy standalone reference page together; otherwise modules like `std.testing` drift out of the `language/reference/stdlib/` structure even when release notes and how-to docs were updated. (Issues #301/#302)
- **RFC lifecycle edits need graph updates**: When an RFC is renamed, moved, split, or superseded, update inbound RFC references and regenerate `workspaces/docs-site/docs/_snippets/rfcs_refs.md` plus `workspaces/docs-site/docs/_snippets/tables/rfcs_index.md`; otherwise the docs graph silently points at stale RFC paths and statuses. (RFC 012/050/051 split)
- **RFC checklist gaps force replanning**: In a Ralph loop, unchecked RFC `Progress Checklist` items are scope failures, not PR-body residual risks; route them back through Plan -> Do -> Check -> Act before publishing, and only use closing keywords after the RFC is fully checked and bumped. (RFC 084 / issue #453)
- **Ralph worktrees live in encero/tmp**: for `ralph-loop`, every implementation must start in a fresh worktree under the workspace root's `encero/tmp` directory, not a system temp directory and not the primary checkout, so VS Code discovers the workspace and orchestration stays consistent. (RFC 016 / issue #327)

## Builtin trait stubs and stdlib method lookup (#193)

- **Vocabulary-only builtin traits ship with empty `methods` maps** in the symbol table. For instance method resolution, `trait_method_info_resolved` can fall back to `StdlibAstCache::lookup_trait` after `stdlib_module_segments_for_trait_methods` in `src/frontend/typechecker/check_decl.rs` maps the trait name to a stdlib module path.
- **That path map is limited to `std.derives.{copying,string,comparison}`** (Clone/Default/Debug/Eq/…). Traits defined under other stdlib prefixes—**example:** `Serialize` / `Deserialize` in `std.serde.json`—are **not** discovered by this fallback. Extending derive-backed instance methods for those traits means adding entries (short term) or a **registry-driven** trait→module mapping (long term), not duplicating path logic in scattered call sites.

## Generic bounds and extern functions

- **Store explicit generic bounds in frontend symbols**, not just type-parameter names. A per-parameter bounds map lets call checking enforce `with` contracts before lowering.
- **Extern diagnostics need CLI-level wrapping**: typechecker catches declaration-shape issues, but signature/path mismatches fail in Cargo. Map rustc stderr back to `@rust.extern` spans for actionable diagnostics.
- **Centralize shared typechecker heuristics immediately**: if a naming rule or predicate is used in more than one checker module, extract it to a shared helper to avoid silent drift.
- **Manifest-backed type conversion must have one source of truth**: keep `TypeRef` ↔ `ResolvedType` mapping in a shared helper/module and reuse it across typechecker/LSP/codegen consumers. Duplicated conversion logic drifts and causes hard-to-debug manifest import regressions.

## RFC 041 (first-class Rust interop) implementation notes

- **Guardrail tests reject hardcoded builtin trait literals in compiler layers**: even in tests, avoid exact string literals like `"Clone"` in assertions; use `incan_core::lang::traits::as_str(TraitId::Clone)` (or equivalent canonical vocabulary helpers).
- **Examples runner can pick a stale repo-local release binary when `CARGO_TARGET_DIR` is redirected**: in Cursor/CI-like environments, Cargo may build to a non-default target dir while `scripts/run_examples.sh` prefers `./target/release/incan`. If this mismatch appears, pass `INCAN_BIN="$CARGO_TARGET_DIR/release/incan"` or make the script fallback aware.
- **Metadata-backed interop needs default-path coverage**: `rust-metadata` is optional, so Rust interop fixes that rely on canonical metadata must also preserve the default build path when receiver provenance degrades or the feature is off. For method lowering/coercion bugs, test both the metadata-enhanced path and a plain default build of a real interop example. (Issue #236)
- **`rusttype` example checks should be feature-aware**: `examples/rust_interop_rusttype/main.incn` can fail default smoke checks when relying on metadata-backed/static rebinding behavior that is only validated under `rust-metadata` feature paths. Keep a clear skip reason in `scripts/run_examples.sh` until that path is fully on by default.
