# incan builds incan — packet 1: inventory and plan (#1698)

This document is packet 1 of #1698 and the record of packet 2's first proof. It inventories every Cargo manifest in the repository as the facts a `loaf.toml` Rust facet must carry, maps those facts onto today's `ProjectManifest`, names what RFC 119's facet model lacks and proposes the manifest extension as an amendment for RFC 119, maps the stored direct-rustc plans onto the facets (the evidence that Oven already builds the compiler's units), and plans packets 2–5 with Cargo-free verification commands. The inventory is generated: `python3 scripts/self_build/cargo_manifest_inventory.py` writes `cargo_manifest_inventory.json` beside this file, `--check` fails when it is stale, `--markdown` prints the table below.

Decisions this document follows (the issue body and the decisions of 2026-09-20): no Cargo invocation on a developer machine; no `Cargo.toml` remains in the repository; stage 0 is the installed toolchain archive, never Cargo; clippy is the one temporary exception (CI) until packet 4; lint configuration lives in `loaf.toml` as `[rust.lints]` with Cargo's `[lints]` semantics — there is no `clippy.toml` — and in-source `#![deny(clippy::…)]` attributes stay because they are code.

### RFC 119 amendment proposal (whether it lands as an amendment or a new RFC is decided when packet 2 starts)

A1. **`[[rust.bin]]` — binary roles (landed as code in this packet).** Shape: an array of tables `[[rust.bin]] name = "<executable>" path = "<root .rs, project-relative>"`. Semantics: a build role of this Loaf's own Rust unit (RFC 119 design decision "`rust.*` exceptions describe one Loaf's own single compilation unit … plus additional build roles"); the conventional `src/main.rs` under the project's name needs no declaration, and neither do the conventional `src/bin/*.rs` binaries (RFC 119's guide: `src/bin/` is a conventional location that requires no restatement — the four `generate_*` generators stay undeclared); a plain `incan build` of a Loaf that declares roles and no `[project.scripts].main` builds the roles. Refusals: empty or non-identifier name (ASCII letters, digits, `-`, `_`); a path that is absolute, has `..`, is not a `.rs` file, or lies outside `[rust.source].root` when one is declared ("a binary outside it is another unit, which is a sibling Loaf rather than a role of this one"); duplicate names or paths. Implemented: `RustBinaryRole` (`manifest.rs:515`), `validate_rust_binary_roles` (`manifest.rs:1325`), tests `a_rust_loaf_declares_the_binaries_convention_cannot_name`, `a_rust_binary_role_must_select_one_binary_of_this_loaf_s_own_unit`.

A2. **`[rust] crate-type` and `[rust.lib]` — the library role.** The crate name is always the project name with `-`→`_` (every workspace crate's explicit `[lib] name` — `incan_cli`, `incan_lsp`, `oven_cli` — is exactly that derivation, so no `name` key is needed). Shape: `[rust] crate-type = ["proc-macro"]` for a procedural-macro Loaf, the spelling RFC 119's own design-decision example uses (the host-domain unit its rule 4 of "Build scripts, procedural macros" describes; replaces Cargo's `proc-macro = true`), `[rust] crate-type = ["rlib", "cdylib"]` for the vocab companions; `[rust.lib] path = "src/lib.rs"` only when the root is not conventional, `doctest = false` to switch the doctest root off. Refusals: `crate-type = ["proc-macro"]` together with a `[[rust.bin]]` role or with another crate type (a proc-macro unit is one crate type); `path` outside the Rust root; a `[[rust.bin]]` role named like the library is allowed (Cargo allows a same-named lib and bin) but two libraries are refused (one unit per Loaf).

A3. **Workspace-internal crates as dependencies.** A workspace crate is a `loaf`-kind dependency written with the explicit `loaf =` key in `[dependencies]`: `incan_frontend = { loaf = "incan_frontend", path = "loaves/compiler/incan_frontend", default-features = false }` (a member may write `{ loaf = "incan_frontend", workspace = true }` against a root `[workspace.dependencies]` entry of the same shape, adding `features` where Cargo did). This is RFC 119's own example (`{ loaf = "incan_derive", path = "loaves/incan_derive" }`) and RFC 117 "Typed dependencies" makes the unit kind an authored fact — one the lock records — rather than something derived from the target manifest's facets, so a derived-kind reading is not adopted: the author names the kind, and the resolver refuses a `loaf`-kind entry whose target has no `loaf.toml` or a `crate`-kind entry pointed at a workspace Loaf. Nothing parses `loaf =` today (`[dependencies]` is an untyped table, `manifest.rs:670`); packet 2 adds it. `[rust-dependencies] incan_frontend = { workspace = true }` with a root `[workspace.rust-dependencies]` path entry — the grammar the stdlib components use today — stays accepted as the named transitional form and is retired with packet 5, when the lock records every workspace edge as `loaf`-kind.

A4. **`[workspace.project]` — shared identity.** Shape: `[workspace.project] version = "0.6.0-dev.6" license = "Apache-2.0" authors = […] repository = … homepage = … edition = "2024"`; a member writes `version.workspace = true` (same spelling as Cargo, same set of inheritable keys). The Oven and stdlib rings keep their explicit versions exactly as they do in Cargo (`scripts/check_ring_versions.py` keeps reading the root table). Refusals: `key.workspace = true` for a key the root does not declare; a root without `[workspace]`.

A5. **Feature mapping for a Rust unit.** `[project.features]` stays the public feature surface (RFC 114). Add the explicit mapping RFC 119 rule 5 requires: a Loaf feature `f` enables `--cfg feature="f"` on the Loaf's own Rust unit when the manifest says so — `[rust] features = ["rust_inspect", "std_testing", …]` names which project features are also `cfg` features of the unit (default: every feature name declared in `[project.features]`, which is Cargo's behaviour and what the stored plans' closures record); `dep:x` and `x/feature` edges keep their `ProjectFeatureDefinition` forms. The lock records the selected closure per unit, as the stored `OvenCompilerWorkspaceLibraryKey.features` already does.

A6. **`[rust.lints]` — lint configuration (decided 2026-09-20).** Shape and semantics identical to Cargo's `[lints]`: `[rust.lints.rust] unsafe_code = "forbid"`, `[rust.lints.clippy] unwrap_used = "deny"`, `[rust.lints.clippy.pedantic] level = "warn" priority = -1`, levels `allow | warn | deny | forbid`, groups with `priority` ordering lower-first, `warnings = "deny"` for the `-D warnings` policy; also inheritable as `[rust.lints] workspace = true` from `[workspace.rust-lints]` (the toolchain wants one policy). Oven turns the table into `-A/-W/-D/-F` flags per unit, in priority order, on the `rustc` (packet 2) and `clippy-driver` (packet 4) command lines; an unknown level or a non-identifier lint name is refused at parse time; there is no `clippy.toml`. A lint entry may carry configuration beside its level: `[rust.lints.rust.unexpected_cfgs] level = "warn" priority = 0 check-cfg = ["cfg(bootstrap)"]` is the one configuration key Cargo's `[lints]` admits, and Oven passes each `check-cfg` element as a `--check-cfg` flag of the unit (it is not a lint level); any other configuration key on a lint entry is refused with the key named. In-source `#![deny(…)]` attributes are code and stay. Migration: the third-party patch's `[lints.clippy]` and `[lints.rust]` tables transcribe verbatim into `[rust.lints.clippy]` and `[rust.lints.rust]` (including `unexpected_cfgs.check-cfg`); CI's command-line `-D warnings` becomes `[workspace.rust-lints.rust] warnings = "deny"` at the root, inherited by every member (`warnings = "deny"` is Cargo's own spelling for it).

A7. **Toolchain and profile facts at the workspace root.** `[rust] toolchain = "1.98.0"` (replaces `rust-version`; RFC 119 makes the toolchain a receipt coordinate — one selected compiler for the workspace) and `[rust.profile.<name>]` for the two facts the workspace needs: `[rust.profile.oven-test] debug = false incremental = false` (already the runner's contract) and `[rust.profile.dev.package.sha2] opt-level = 3` (a per-dependency codegen override; refuse any key the direct-rustc planner does not map to a `-C` flag). Anything else Cargo's profiles express is not carried.

A8. **Strict facet parsing with a version bound the bootstrap answers (requirement found by the proof).** Stage 0 is the installed toolchain archive, by definition older than the manifests it must read. Today `RustTables` is `deny_unknown_fields` (`manifest.rs:1180`), so an installed stage 0 that predates `[[rust.bin]]` refuses the member manifest that declares it (`failed to parse …/incan-cli/loaf.toml:8:8: unknown field 'bin'`), and with it every `incan` command run inside the tree. Decision: keep `deny_unknown_fields` — a facet the compiler cannot read is refused, never skipped — and make the bootstrap answer the version bound instead: the `requires-incan` and `requires-oven` bounds (`[project]` on a member, `[workspace.project]` at a virtual root; RFC 117 defines both, only `requires-incan` is parsed today) are read from the raw TOML document before the typed parse, so an older stage 0 reports "this workspace requires incan ≥ X" rather than an unknown-field error, and an unknown-field error that does surface under `rust.*` names that bound in its message. The non-adoption rule of the gate below (a Loaf without an Incan facet is never a `.incn` file's project) is likewise decided on a raw-document facet probe — the presence of `[rust.source]`, `[rust.lib]`, `[[rust.bin]]` or `[rust] crate-type` — so an older stage 0 can apply it before the typed parse it would fail. The stage 0 that reads a change adding facet grammar is the freshly built `incan` (CI builds it with Cargo until packet 5); the warm template is refreshed locally when the grammar changes.

A9. **Rust-only Loaf convention.** RFC 119 says a conventional Rust-only Loaf "needs no Rust table"; today `[rust.source] root = "src"` is refused as overlapping the Incan root (`manifest.rs:1610`), and a manifest without `[rust.source]` is an Incan project whose `src/` is Incan source. Proposal: a Loaf declares its facets by presence — an Incan facet exists when `[build].source-root` is set or `src/` holds `.incn` sources, a Rust facet when `[rust.source]`, `[rust.lib]`, `[[rust.bin]]` or `[rust] crate-type` is declared or `src/lib.rs`/`src/main.rs` exists — and the overlap refusal applies only when both facets are present. This is what lets `loaves/toolchain/incan-cli/loaf.toml` say nothing but `[[rust.bin]]`.
