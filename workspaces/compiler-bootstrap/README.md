# Compiler bootstrap recovery

This workspace contains Incan orchestration for the source compiler development loop in #1698. It consumes the published native SDK and the existing Oven receipt, selection and execution APIs. It does not resolve dependencies, authorize an SDK from a source directory, or copy the SDK closure.

The compiler CLI library and its dependencies must already be admitted and prepared. The entrypoint internally prepares the Incan native-runtime identity engine and binds its executable alongside the CLI source tree. It holds the selected owners throughout binary compilation, and reports the exact receipt, build-unit and output identities. These outputs must still be checked against executed fixture behavior before claiming the developer-loop acceptance contract in DD-0005.

The report separates source/request preparation, prepared SDK selection and compiler execution or reuse. The successful execution adapter returns `reused` only when its byte-bound output receipt admits the retained binary before invoking rustc. The reported compiler invocation count is therefore zero for that branch and one for the successful compilation branch. SDK compilation is zero because this entrypoint only selects prepared units. The report does not yet count physical compilation of the identity engine; its preparation transcript is retained beside the compiler. These counts cover the compiler bootstrap call; they do not describe fixture compilation, SDK preparation in an earlier command, or the whole development loop. A compilation decision reports that the output required compilation, without guessing which input caused the miss.

`make build-fast` and `make build-quiet` also call this Incan bootstrap and publish the compiler, original receipt, output sidecar and identity engine under `target/debug`. Both retain their compiler-only scope. The quiet command retains its bootstrap report under `target/compiler-development/command-evidence/quiet.*`; errors remain visible. The shared shell transport installs the Cargo guard before SDK preparation and keeps it active through execution, just as `make test-one` does. It contains no dependency or reuse policy. `CARGO_TARGET_DIR` remains a compatibility spelling for redirecting the Make output root. `INCAN_SKIP_CARGO_BIN_LINK=1` skips the local PATH links; CI skips them by default.

These development commands still need a stage zero compatible with the current native SDK; select a retained compatible compiler with `INCAN_TEST_BOOTSTRAP_COMPILER` when the installed compiler predates that SDK. This does not establish installed-stage compatibility or retire the other build, release, LSP, lint and full-suite entrypoints.

`compiler_bootstrap --inspect-authority FIXTURE_ROOT` observes the source, dependency and materialized-provider identities of the retained `library`, `lowering` and `driver` fixture nodes. It performs no compilation and grants no reuse authority. Comparing observations before and after fixture preparation helps distinguish authored changes from provider handoff churn.

The internal `--test SOURCE_ROOT TEST_ROOT EXACT RUSTC STORE` mode first builds or reuses the source-bound compiler. It runs the existing native test kernel with a persistent, worktree-owned binary location and retains command output and reports in a separate directory for each invocation. An empty `EXACT` selects the complete root. The native kernel still validates source containment, authored dependencies, receipts and the real case inventory. This orchestration does not delete the prepared binary after successful execution. Baseline runtime validation passed the complete 109-case Oven-store root and its unchanged repeat, reusing the source compiler and test binary. A separate compatible-worktree snapshot passed all 109 cases three times, but its first repeat rebuilt both outputs before the next repeat stabilized; first-repeat JEC remains unfulfilled in that control; a missing-case control failed without a current success report. `make test-one` now calls this mode through the ordinary `incan run` command. The Make path passed the same root under the outer Cargo guard and published the optional report and transcript archive while retaining the prepared binary. A deliberate Cargo call was refused by the guard. Acceptance still requires a fixture that bakes the compiler graph, installed-stage-zero compatibility and Cargo metadata retirement.

## Declared dependency optimization

The independent [compiler-unit-codegen workspace](../compiler-unit-codegen/README.md) binds the internal compiler profile declaration to exact units in a schema-2 Loaf resolution. It preserves the resolver's units, sources, features and edges. Its development declaration optimizes SHA-256 while explicitly retaining assertions and overflow checks; it does not switch that dependency to release semantics.

The native adapter carries the declared options into the unit receipt before output lookup and applies them after the named profile's defaults. An option change therefore selects a different receipt and dependent output identities. The transport is tracked as removable #1698 debt in `repros/unit_codegen.md`. Units with build scripts require facts bound to the chosen options; the current adapter refuses their override because existing profile-only facts do not establish those inputs. No named dependency gets a special case in the Rust adapter.

The Incan declaration tests prove binding and refusal behavior only. They do not establish that the physical executor applies the flags, that a prepared SDK contains the optimized output, or that the resulting compiler is faster. Those require separate runtime and identity evidence.

## Acceptance still required

The local recovery chain used a retained development compiler. Installed 0.5.1 rejects the current SDK's compiler requirement. The retained experimental stage zero still has an adjacent Cargo lock in its old toolchain layout. The rebuilt source compiler runs the selected numeric comparison without an adjacent lock and uses the Incan native-runtime projection. Remaining Rust path-source authority and freshness readers still inspect Cargo manifests. Selected execution does not establish complete Cargo metadata retirement or installed-toolchain acceptance.

The initial numeric comparison failed because the formatting caller published its runtime under the caller's output tree, while the test expected a source-root runtime receipt. An explicit runtime preparation enabled the comparison and the subsequent guarded repeat. That diagnostic workaround is not the ordinary-command fix. The later ordinary Make path automatically prepares its declared fixture helper and passes the numeric comparison plus its guarded repeat. A controlled Add-to-Subtract lowering edit changed the dependent driver and failed byte parity as intended while retaining unrelated compiler/library outputs. Its first unchanged repeat exposed a separate package-cache transaction defect; the edit is restored, and normal parity passes again. Edited-source JEC, compatible-worktree reuse, full-suite and census acceptance remain open.

## Temporary interop bridges

The bridges below are removable debt tracked by [#872](https://github.com/encero-systems/incan/issues/872). They do not move orchestration or dependency policy into Rust.

- `ProjectManifest.rust_dependency_values` materializes the existing dependency records because stage zero rejects `.values()` and `.clone()` on the borrowed map returned by `rust_dependencies()`. The minimal source is `repros/borrowed_map.incn`; the diagnostic is `Type '&Dict[str, rust::oven_model::manifest::DependencySpec]' has no method 'values(...)'`.
- `OvenTrustedDirectRustcTargetRequest.new` exposes construction through a function argument boundary. Struct field construction rejects `features: list[str]` with `expected '&oven_rustc::rustc::[String]', found 'List[str]'`; the list has no `as_slice()` method. The function boundary also rejects a list for a slice parameter. The constructor therefore borrows the feature set already declared by the receipt, alongside the same receipt, plan and paths that the caller holds through execution.

Remove each bridge when the corresponding borrowed-container or struct-field conversion works through ordinary Incan Rust interop. Validate the current constructor path at runtime before relying on it; a Rust build or an Incan typecheck alone is insufficient.

## Initial shared identity-engine selection

The bootstrap now attempts source-current shared engine selection before invoking its internal preparation command. Incan checks the exact stage-zero executable digest, dependency authority, lock fingerprint, native target and toolchain. The existing selection API validates the source-current stored payload and returns lease owners; the existing native verifier checks its immutable executable before the Incan projection copies bytes. A miss takes the existing preparation route and must select an admitted shared output afterward.

The selection-only executable passed first use and unchanged reuse, repaired tampered/read-only/symlink projections, and refused changed source, lock fingerprint and compiler identity. The unchanged invocation retained the same caller projection inode and timestamp; the immutable store output retained its bytes, mode, inode and timestamp. These controls do not prove whole-loop compilation counts. The complete 109-case store-root Make command also passed after the SDK change; its immediate guarded unchanged repeat reused both compiler and native test binary. Kernel reports counted zero compiler and zero SDK compilations on the repeat, and the engine preparation transcript remained unchanged. Other selected roots, edited-package reuse, compatible compiler-binary sharing and full-suite acceptance remain open. The first direct Incan call to the public matcher panicked on its `Option<(&str, &str)>` argument. The reduced repro is `repros/optional-tuple-api-gap`. The temporary #872 adapter only supplies that optional `None` argument; selection acceptance remains in Incan. This is separate from compiler binary sharing and from the package-cache retention defect. Do not infer whole-loop reuse from a successful projection or from a later stabilized repeat.
