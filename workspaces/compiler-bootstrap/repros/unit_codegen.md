# Native compiler dependency codegen input gap

Tracked by [#1698](https://github.com/encero-systems/incan/issues/1698). The compiler development profile already declares optimization for SHA-256 in the retained Cargo manifest. Cargo retirement must preserve that behavior through explicit Oven inputs; a debug-to-release substitution would also change assertion and overflow semantics.

The current `ClosureCompileRequest` exposes one `profile` for every adopted unit. The seed accepts only `schema` and `units`, and the compiler graph accepts only `index_commit`, `registry_lock` and `facets`. A graph carrying a per-unit declaration is refused with `unknown field unit_profiles`. The retained negative-control transcript is `compiler-profile-repro.log` in the recovery evidence directory. Inspection of `unit_receipt` and the direct execution adapter confirms that no per-unit codegen argument can currently be supplied through the public Incan interop boundary.

`workspaces/compiler-unit-codegen/src/unit_codegen.incn` owns selection policy: it binds an explicit declaration to one exact locked Loaf, version and domain, validates optimization and boolean assertion options, and preserves all resolver-owned source, feature and edge records. Its `compiler-unit-codegen.json` declares the development SHA-256 optimization with assertions and overflow checks enabled. These declarations do not yet make the executor apply those options.

The required adapter is a generic transport and execution boundary for these receipt-bound codegen options. It must not recognize SHA-256 by name, choose a compiler profile, resolve a dependency, inherit ambient flags, or authorize reuse by an unbound option. Changing the options must change the unit receipt before lookup, and execution must apply exactly those options. The seed-to-receipt transport is removable debt until the adopted-unit orchestration is authored in Incan and supplies the same declared options directly to the native execution boundary.
