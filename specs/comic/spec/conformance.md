# Foundation corpus

The [manifest](../corpus/manifest.json) lists every case file, its SHA-256 and its test operation. JSON is a language-neutral test notation here, not a candidate wire encoding. Exact integers and bit patterns are strings so a JSON parser cannot round them. Files are UTF-8. Case IDs are unique across the manifest.

## Operations

- **member_identity**: each case supplies earliest_name and expected six-byte lowercase hex. SHA-256 the exact UTF-8 name, take its first six bytes, and compare. No prefix, suffix or terminator is added. The known collision is intentional; an admission case separately refuses two colliding members in one description.
- **value_relation**: compare the two fully tagged values under crumb1; expect same or distinct value contribution, not a literal digest. Normalize NaN and representation-preserving width/optional wrappers as specified. Strings preserve code points. References compare their target identities without loading targets. No user equality code may run.
- **shape_admission**: validate a written description's ordered fields; expect accepted or the specified failure class and field path. IDs are explicit bytes; display names cannot repair duplicates.
- **adaptation**: read values under the written description into the requested description; expect typed field values or a failure. Source fields are in written identity order. Requested declaration order may differ. Absent values may be supplied only by the explicit policy. The original stored value is unchanged.
- **text_read**: read the COMIC file named by input_file under a description; expect a tagged value, or a failure class and the input's line and column. Inputs may use any whitespace and comments the [text rules](text.md) accept.
- **text_print**: print a tagged value under a description; expect the exact canonical file named by expected_file, byte for byte, including the final newline. A case that also appears in `text_read` must read its own expected text back to the same value. Expected texts are written by hand, never generated by the implementation under test.

## Test notation

A scalar type is a string: boolean, i8, i16, i32, i64, u8, u16, u32, u64, fp32, fp64, string or binary. A compound type is an object with kind and item (option/list) or items (tuple). A description has nominal and fields. Each field has id, name, type, canonical and absent; absent is required, none or empty. Names are diagnostic labels. A schema with absent=none must have an option type; absent=empty requires a collection. Arrays of fields in written descriptions must be strictly ID-sorted. Requested descriptions express declaration order, which the adapter must not confuse with written slot order.

A tagged value has kind and its payload: int uses decimal value and type; float uses width and fixed-width hexadecimal bits; string uses value; binary uses lowercase hex; none has no payload; some has value; list/tuple have items; reference has target_type and identity. References may carry observed_target for a test control: it is not part of the reference value and is never resolved. Representation-preserving wrappers can compare equal as contributions even when the input types differ. These tests do not grant structural compatibility between unrelated nominal models.

Adaptation inputs give values as an array aligned with written fields. Successful outputs give values aligned with requested fields. expected contains status and, on refusal, kind and path. path uses a field's identity, or /nominal for the record identity. A removed field is not returned; that does not mutate the source. comparison expectations describe the logical hash projections, not a promise that an unimplemented hash encoder has a particular digest.

## Text operation notation

The `comic.text/1` corpus pins the settled portion of the experimental text rules, not an implemented parser. Each `text_read` case refers to its byte-exact COMIC file in `input_file`, relative to the corpus directory. An accepted expectation has a `document` with `descriptions` and an ordered `values` list. Core descriptions carry `path`, `kind` and fields in **declaration order**; enum descriptions carry variants with their payload fields. The fields carry name, type, absent policy and canonical flag. Type strings use the core text spellings. Unlike a binary written description, this declaration list must not be sorted by member identity. Member identities are derived from earliest names when building a stored shape.

A record value has `kind=record`, `type` and a `fields` object keyed by declaration name, including explicit absent values. An enum adds its `variant` and payload `fields`. A union names its selected `member` and `value`. Decimal values have an exact integer `coefficient`, `precision` and `scale`. Boolean values use `kind=boolean` and a JSON Boolean; binary uses `kind=binary` and `hex`. A withheld value has `kind=withheld` and its secret `type`, with no contents. Maps have ordered `entries` of key/value pairs; sets have `items`. Optional layers use `none` and `some`. This is test data, not code that a reader evaluates.

A `text_print` case takes that same document and names its exact UTF-8 output in `expected_file`, relative to the corpus directory. Its `read_case` identifies an accepted read case with the same typed document. A runner must additionally read the expected printed text and compare the resulting document. The expected `.comic` file is authored independently of the printer. Shared identical input and output bytes use one file. Description ordering in the document expectation is semantic: compare descriptions by path and kind, fields by declaration order and values in order.

Refusal locations are one-based lines and Unicode-scalar columns. An unexpected end points just past the input. A duplicate points to its second cell or same-kind declaration; a value type with no single value-bearing declaration points to that value's type; an unknown or invalid token points to its beginning. A missing required field points to the closing record delimiter. Error `kind` is a language-neutral category, not a required diagnostic code or wording. A runner may retain richer spans but must include this location. Warning diagnostics for confusable identifiers do not turn a valid read into a refusal.

The cases distinguish truncation inside an entry from a cut at an entry boundary, indexes on input from names on output, and a single value from a one-row table. They also distinguish nested row groups from a single nested record and from a heterogeneous union list. No cases freeze the still-open date/time spellings, store identity text, multi-line string printer selection or wrapping of a line over 120 characters. Those require additional cases when their exact rules are fixed.

## What is and is not proved

This foundation checks member identities, optional and float distinctions, Unicode preservation, references, descriptor ordering/collisions and common evolution decisions. It specifies text read/print outcomes but does not yet prove a COMIC parser, a Crumb binary codec, record streaming, memory bounds or full recursive type support. Those remain required by [text](text.md), [binary](binary.md) and [values](values.md). No implementation is declared conformant by committing these files.

Implementations must run the data files directly. They may not copy a selection of cases into source and call that full conformance. Add an implementation receipt naming corpus revision, profile, selected cases, outcomes and known unsupported cases. A host may have stricter caller-selected resource limits; report limit refusals separately from malformed data.

## Independent checks

The email and customer identity vectors agree with the existing derivation examples; all vectors can be independently computed with any SHA-256 implementation. The pair fieldbbea15ef9eff and field3d4624c2d3a2 intentionally has equal six-byte prefixes. The signed-zero and NaN cases use explicit IEEE binary32/binary64 bits; the Unicode cases use distinct scalar sequences. These controls keep host-language equality, JSON numeric rounding and pretty text from becoming an accidental oracle.

## Self-description follow-up

When the text grammar is defined, profiles, the corpus manifest and case data also receive COMIC representations. Keep their independent JSON twins and test that each COMIC document reconstructs exactly its twin's typed values. Do not generate both expected and actual values solely through the same parser. Prose remains Markdown. Descriptions of the format's own profile, field and case models can follow once those models and their text grammar are precise; this foundation adds no guessed COMIC files.

## Readable text fixtures

Every COMIC input and expected output is a separate file under [corpus/text](../corpus/text/). The manifest's `text_files` list pins their SHA-256 values. The directory's `.gitattributes` disables Git text conversion and whitespace linting: a truncated value, missing final newline or raw prohibited control stays byte-exact. Typed expected values remain independent JSON data. Do not regenerate them by parsing the expected COMIC files.
