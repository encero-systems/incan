# Foundation corpus

The [manifest](../corpus/manifest.json) lists every case file, its SHA-256 and its test operation. JSON is a language-neutral test notation here, not a candidate wire encoding. Exact integers and bit patterns are strings so a JSON parser cannot round them. Files are UTF-8. Case IDs are unique across the manifest.

## Operations

- **member_identity**: each case supplies earliest_name and expected six-byte lowercase hex. SHA-256 the exact UTF-8 name, take its first six bytes, and compare. No prefix, suffix or terminator is added. The known collision is intentional; an admission case separately refuses two colliding members in one description.
- **value_relation**: compare the two fully tagged values under crumb1; expect same or distinct value contribution, not a literal digest. Normalize NaN and representation-preserving width/optional wrappers as specified. Strings preserve code points. References compare their target identities without loading targets. No user equality code may run.
- **shape_admission**: validate a written description's ordered fields; expect accepted or the specified failure class and field path. IDs are explicit bytes; display names cannot repair duplicates.
- **adaptation**: read values under the written description into the requested description; expect typed field values or a failure. Source fields are in written identity order. Requested declaration order may differ. Absent values may be supplied only by the explicit policy. The original stored value is unchanged.
- **text_read**: read the COMIC file named by input_file under a description; expect a tagged value, or a failure class and the input's line and column. Inputs may use any whitespace and comments the [text rules](text.md) accept.
- **text_print**: print a tagged value under a description; expect the exact canonical file named by expected_file, byte for byte, including the final newline. A case that also appears in `text_read` must read its own expected text back to the same value. Expected texts are written by hand, never generated by the implementation under test.

- **hash_preimage**: derive the exact preimage from the logical input under its named projection, then compare SHA-256. Concatenating the annotated literal segments is an additional check, not the derivation. Model inputs supply a type tree; description inputs supply the complete metadata tree; seals supply an ordered values list.
- **nominal_identity**: UTF-8 encode registry, package and earliest_path with one zero byte after each, hash the resulting bytes without a domain prefix, then take six bytes. Compare the full literal input and digest too. The fields may not contain zero bytes.

## Test notation

A scalar type is a string: boolean, i8, i16, i32, i64, u8, u16, u32, u64, fp32, fp64, string or binary. A compound type is an object with kind and item (option/list) or items (tuple). A description has nominal and fields. Each field has id, name, type, canonical and absent; absent is required, none or empty. Names are diagnostic labels. A schema with absent=none must have an option type; absent=empty requires a collection. Arrays of fields in written descriptions must be strictly ID-sorted. Requested descriptions express declaration order, which the adapter must not confuse with written slot order.

A tagged value has kind and its payload: int uses decimal value and type; float uses width and fixed-width hexadecimal bits; string uses value; binary uses lowercase hex; none has no payload; some has value; list/tuple have items; reference has target_type and identity. References may carry observed_target for a test control: it is not part of the reference value and is never resolved. Representation-preserving wrappers can compare equal as contributions even when the input types differ. These tests do not grant structural compatibility between unrelated nominal models.

Adaptation inputs give values as an array aligned with written fields. Successful outputs give values aligned with requested fields. expected contains status and, on refusal, kind and path. path uses a field's identity, or /nominal for the record identity. A removed field is not returned; that does not mutate the source. comparison expectations describe the logical hash projections, not a promise that an unimplemented hash encoder has a particular digest.

## Text operation notation

The `comic.text/1` corpus pins the settled portion of the experimental text rules, not an implemented parser. Each `text_read` case refers to its byte-exact COMIC file in `input_file`, relative to the corpus directory. An accepted expectation has a `document` with `descriptions` and an ordered `values` list. Core descriptions carry `path`, `kind` and fields in **declaration order**; enum descriptions carry variants with their payload fields. The fields carry name, type, absent policy and canonical flag. Type strings use the core text spellings. Unlike a binary written description, this declaration list must not be sorted by member identity. Member identities are derived from earliest names when building a stored shape.

A record value has `kind=record`, `type` and a `fields` object keyed by declaration name, including explicit absent values. An enum adds its `variant` and payload `fields`. A union names its selected `member` and `value`. Decimal values have an exact integer `coefficient`, `precision` and `scale`. Boolean values use `kind=boolean` and a JSON Boolean; binary uses `kind=binary` and `hex`. A withheld value has `kind=withheld` and its secret `type`, with no contents. Maps have ordered `entries` of key/value pairs; sets have `items`. Optional layers use `none` and `some`. This is test data, not code that a reader evaluates.

A `text_print` case takes that same document and names its exact UTF-8 output in `expected_file`, relative to the corpus directory. Its `read_case` identifies an accepted read case with the same typed document. A runner must additionally read the expected printed text and compare the resulting document. The expected `.comic` file is authored independently of the printer. Shared identical input and output bytes use one file. Description ordering in the document expectation is semantic: compare descriptions by path and kind, fields by declaration order and values in order.

Refusal locations are one-based lines and Unicode-scalar columns. An unexpected end points just past the input. A duplicate points to its second cell or same-kind declaration; a value type with no single value-bearing declaration points to that value's type; an unknown or invalid token points to its beginning. A missing required field points to the closing record delimiter. Error `kind` is a language-neutral category, not a required diagnostic code or wording. A runner may retain richer spans but must include this location. Warning diagnostics for confusable identifiers do not turn a valid read into a refusal.

The cases distinguish truncation inside an entry from a cut at an entry boundary, indexes on input from names on output, and a single value from a one-row table. They also distinguish nested row groups from a single nested record and from a heterogeneous union list. No cases freeze the still-open date/time spellings, store identity text, multi-line string printer selection or wrapping of a line over 120 characters. Those require additional cases when their exact rules are fixed.

## What is and is not proved

This foundation checks member identities, optional and float distinctions, Unicode preservation, references, descriptor ordering/collisions and common evolution decisions. It specifies text read/print outcomes but does not yet prove a COMIC parser, a Crumb binary codec, record streaming, memory bounds or full recursive type support. Those remain required by [text](text.md), [binary](binary.md) and [values](values.md). No implementation is declared conformant by committing these files.

Implementations must run the data files directly. They may not copy a selection of cases into source and call that full conformance. Add an implementation receipt naming corpus revision, profile, selected cases, outcomes and known unsupported cases. A host may have stricter caller-selected resource limits; report limit refusals separately from malformed data.

## Independent checks

The email and customer identity vectors agree with the existing derivation examples; all vectors can be independently computed with any SHA-256 implementation. The pair fieldbbea15ef9eff and field3d4624c2d3a2 intentionally has equal six-byte prefixes. The signed-zero and NaN cases use explicit IEEE binary32/binary64 bits; the Unicode cases use distinct scalar sequences. These controls keep host-language equality, JSON numeric rounding and pretty text from becoming an accidental oracle.

## Self-description follow-up

When the text grammar is defined, profiles, the corpus manifest and case data also receive COMIC representations. Keep their independent JSON twins and test that each COMIC document reconstructs exactly its twin's typed values. Do not generate both expected and actual values solely through the same parser. Prose remains Markdown. Descriptions of the format's own profile, field and case models can follow once those models and their text grammar are precise; this foundation adds no guessed COMIC files.

## Readable text fixtures

Every COMIC input and expected output is a separate file under [corpus/text](../corpus/text/). The manifest's `text_files` list pins their SHA-256 values. The directory's `.gitattributes` disables Git text conversion and whitespace linting: a truncated value, missing final newline or raw prohibited control stays byte-exact. Typed expected values remain independent JSON data. Do not regenerate them by parsing the expected COMIC files.

## Digest-vector notation

Digest records contain identity-sorted or deliberately shuffled `fields`, each carrying `id`, `type`, `canonical`, `absent` and `value`. Projection sorting happens during hashing, not in the test loader. An enum has `variant_id` and a record `payload`. A union has a `member_type` (its declaration identity is `nominal_hex`, with ordered `arguments` for a closed generic) and a `value`. A model input wraps a structural tree in `type`; records/enums have a local test `key`, and a recursive edge uses `kind=recur` and the same key. Those test keys never enter a preimage. Map types use `key_type` and `value_type`, tuples/unions use `items`. Model scalar type strings use the canonical spelling in hashes.md.

A `derivation` lists annotated literal byte segments; it is an explanation of the expected bytes, not executable codec code. Independently re-derive the bytes from `input`. Changes to ignored reference observations, integer width or noncanonical key fields are paired controls; reversal of a sealed set, a selected nominal union member, or the sign of zero changes its hash.

Description metadata uses tagged null/Boolean/integer/string/binary/list/map values, as D defines in hashes.md. Field absence is explicit in each model type tree. Declaration identity hex in union selectors is exactly six bytes and agrees with the separately supplied three-string derivation.

## Row byte vectors

`binary-row.json` selects operation `binary_decode` and codec profile `crumb-row/1`. `input_hex` is the exact single-envelope input, including malformed bytes where intentional. `supplied_descriptions` contains caller-provided complete descriptions in the tagged D metadata notation. An empty list provides no external description; it never authorizes fetching one. A valid description digest does not replace admission checks.

Accepted outcomes contain records in wire order, each with `selector_hex` (the complete K bytes) and identity-sorted `fields`; an enum adds `variant_id`. Field values use the existing typed notation. References use `target_type_hex` and `identity_hex` for opaque bytes. `sealed` reports a successfully verified seal, not merely a set flag. Re-encode every accepted outcome under the original descriptions, dictionary modes and envelope boundary, and compare every byte with the input. `derivation`, where supplied, annotates literal byte segments; it must concatenate exactly to input_hex. Seal preimages, where supplied, are independently derived from logical values under the unchanged hash rules.

Refused outcomes name the category, not a host-specific diagnostic string. `transform=all_proper_prefixes` runs a separate refusal for every prefix length from zero through input length minus one. `require_sealed` is a caller policy. `limits.elements` bounds a collection's count; `limits.depth` counts each entered field cell as one and increases for each nested cell. These are explicit test settings, not universal deployment defaults. Implementations retain the shared budget obligations in row-v1.md.

These cases cover core scalar cells, tuple/list/map/set values, a scalar union, root enum metadata, outer and nested optional absence, declaration-order restoration, description references, seals, offsets and malformed input. They are not yet full recursive containment, nominal-union, cross-description nested-record, streaming or resource-accounting coverage. Production implementations must add and execute those controls before claiming the complete profile. No production decoder, bounded-allocation guarantee or performance result is supplied by this corpus change.

`type_selector` vectors provide a declaration identity and ordered closed arguments, then exact K preimage bytes and N spelling. Empty arguments and the nongeneric form agree; reordered arguments differ. The row corpus also places two closed instantiations of one declaration inside a single value and nests a third instantiation.

Selector-only vectors test encoding after binding admission. They do not establish that an arbitrary supplied declaration accepts the indicated arity or constraints; a language binding must prove those facts before admitting a description.

## Column byte vectors

`binary-columns.json` selects the corpus operation `column_codec` and codec profile `crumb-columns/1`. Each case's `operation` identifies its boundary:

- `column_block` supplies a field `type`, `absent` policy (default required), `logical_count` from 1 through 256 and optional `dictionary_keys_hex` (string/binary) or tagged `dictionary_values` (integer/decimal) from the enclosing admitted column. Decode the block, compare `expected.values` in logical-row order and its `encoding`, then reproduce the exact block bytes. Standalone block cases do not require using every supplied dictionary key: that is a whole-column check.
- `column_dictionary` supplies an admitted dictionary `type`. Decode the entire dictionary, compare `expected.keys_hex` for string/binary or tagged `expected.values` for integer/decimal in sorted order, validate exact restart positions and longest prefixes or minimal positive numeric differences, then reproduce all bytes. Its distinct-count-versus-column-population check belongs to a containing column.
- `column_data` supplies field `type`, optional `absent` and the complete `logical_count`. Decode the column header, its one shared dictionary if present, fixed block boundaries and all values. Compare `expected.values` and `encodings` in block order. Verify global dictionary membership and original-choice re-encoding. Cases with 257 distinct keys and code 256 prove the 256-row block size is not a dictionary cap.
- `binary_decode` supplies a full codec-2 envelope and uses the row corpus's `supplied_descriptions` and `expected.records` notation. Compare logical record order and verified `sealed` status, then re-encode under the original description modes and column encoding choices. A paired case retains the exact same logical seal as its row-profile counterpart.

All inputs are literal `input_hex`. Tagged expected values use the existing exact integer/float/decimal notation. Optional `derivation` segments concatenate exactly to the input and explain its framing; they are not executable expectations. `transform=all_proper_prefixes` requires a separate refusal for each shorter prefix. Explicit limits select host policy for the named case, not format-wide caps. Negative cases name the failure category; a successful decode cannot satisfy a refusal just because a different operation would fail later.

These vectors cover the first flat field-column profile, including nested values through row-coded cells. They do not prove recursive shredding, complete binding admission, production shared resource accounting, arbitrary precision beyond the selected values, streaming transports, borrowed-view safety or performance. A production implementation must run the shared row description/cell corpus as well, add missing recursive/resource cases and state exactly which profiles and operations its receipt covers. Byte equality is tested only with original encoding choices; different valid encodings can hold the same logical values and hashes.

## Description-property test context

Description-property cases supply an explicit local `context`. Its `kind_registrations` map each profile kind to the core `Record` or `Enum` shape. A `property_order` array supplies that kind's declared printing order; `property_groups` supplies the order for a nested group such as a function's `type`. A null `property_order` means the shape is registered but the property's profile semantics are unknown to this reader/printer. An empty registration list does not admit arbitrary kinds. This test context neither changes the profile directory nor authorizes loading or executing profile code. `admitted_type_names` supplies externally described profile type spellings needed by the example; these description-only cases construct no values of those types.

A description's `properties` is an ordered list of `{name, value}` entries, recording read order without relying on JSON object iteration. A `symbol` value retains a name such as `Public` or `Int`; it is data, not an instruction to resolve or call a function. A `property_group` contains another ordered `properties` list. Ordinary string and list values retain the existing tagged notation. This notation tests description reading and printing, not the complete semantics of each language's program records.

Readers retain the property order they encounter. Printers put properties before members, use the supplied declared order where known, and retain read order where the shape registration supplies no property semantics. Known groups compare by property name when checking a print/read round trip, so canonical reordering does not change their meaning. Unknown groups must also preserve their original property sequence. Field and variant declaration order remains unchanged. The Invoice control is exactly 109 columns and prints on one line; the function control independently reverses both outer and nested signature property order; the opaque-kind control uses the same text with and without its required registration.
